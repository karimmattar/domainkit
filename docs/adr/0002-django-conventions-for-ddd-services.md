# 0002. Django's conventions for domain-driven services

- Status: Accepted
- Date: 2026-10-14

## Context

FastAPI leaves project structure open, so each service invents its own:
settings, startup, commands, migrations. Engineers moving between services
pay for that every time. Django's conventions (settings modules, installed
apps, `manage.py`, migrations) are widely known. Django's ORM and request
model, however, do not fit an async, domain-driven service.

## Decision

Build services on FastAPI with Django's project conventions:

- settings modules selected by an environment variable and validated at startup
- `INSTALLED_DOMAINS` (installed apps), each with a `DomainConfig` (`AppConfig`)
- `ROOT_ROUTER` (`ROOT_URLCONF`) and an ordered `MIDDLEWARE` list
- `manage.py` with built-in and per-domain commands
- `makemigrations` and `migrate` over Alembic

Each bounded context is a domain package generated by `startdomain`.

## Consequences

A Django developer can find their way around without a guide. The
conventions are implemented by domainkit and must be maintained there. The
framework does not offer Django's admin or ORM, and does not try to.

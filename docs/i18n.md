# Languages, time zones, and formats

An API answers machines first: clients act on `code` and `type`, which
never change. But people read `detail` and the validation messages, and
they read them best in their own language. domainkit translates the
framework's messages into Arabic, lets projects add their own languages
and messages, shows stored UTC times in the business's time zone, and
writes numbers and dates as each language writes them.

On this page you learn how to:

- answer each request in the caller's language, with `LocaleMiddleware`;
- know what is translated, and what never is;
- mark your own messages with `gettext` and its relatives;
- write, update, and compile catalogs with `makemessages` and
  `compilemessages`;
- show stored times in `TIME_ZONE`, with `localtime` and `localdate`;
- write numbers and dates for people, with `number_format` and
  `date_format`.

The decision is in
[ADR 0039](adr/0039-translate-messages-at-the-boundary.md).

## A first example

A route raises an error with a fixed English message, and a catalog of
the project translates it into Arabic:

```python
from fastapi import APIRouter

from domainkit.ddd import NotFound
from domainkit.http.access import Public

router = APIRouter()


class InvoiceNotFound(NotFound):
    code = "invoice_not_found"


@router.get("/invoices/{number}", dependencies=[Public])
async def read_invoice(number: str) -> dict[str, str]:
    raise InvoiceNotFound("No invoice has that number.")
```

The catalog, `locale/ar/LC_MESSAGES/messages.po`, holds the translation:

```po
msgid ""
msgstr ""
"Content-Type: text/plain; charset=UTF-8\n"

msgid "No invoice has that number."
msgstr "لا توجد فاتورة بهذا الرقم."
```

Compile it with `python manage.py compilemessages`. A client that asks
for Arabic gets the `detail` in Arabic:

```text
GET /invoices/7
Accept-Language: ar-EG, ar;q=0.9, en;q=0.5

HTTP/1.1 404 Not Found
Content-Language: ar
Vary: Accept-Language
```

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "لا توجد فاتورة بهذا الرقم.",
  "instance": "/invoices/7",
  "code": "invoice_not_found",
  "request_id": "71fca473061cc8ebf0f37e5baa895e2d"
}
```

`code` stays `invoice_not_found` in every language, so clients can act on
it.

## Answering in the caller's language

Add `LocaleMiddleware` before `RequestContextMiddleware`, so that the
errors which that middleware, and every later one, answers with are
translated too. New projects list it already:

```python
MIDDLEWARE = [
    "domainkit.http.middleware.ProxyHeadersMiddleware",
    "domainkit.http.locale.LocaleMiddleware",
    "domainkit.http.middleware.SecurityHeadersMiddleware",
    "domainkit.http.middleware.RequestContextMiddleware",
    # ...
]
LANGUAGE_CODE = "en"  # when the caller asks for nothing we have
LANGUAGES = [("en", "English"), ("ar", "Arabic")]
```

- **Choosing the language.** The middleware reads `Accept-Language` and
  picks the language of `LANGUAGES` that the caller prefers most: by `q`,
  then in order. `ar-eg` matches `ar`, and `pt` matches `pt-br`. A
  missing header, `*`, or nothing that matches gives `LANGUAGE_CODE`.
  Malformed ranges are skipped, and only the first 32 ranges (1,024
  characters) are read.
- **For the whole request.** The language is the request's for its whole
  run, in a context variable: `gettext` in endpoints, and tasks started
  from the request, use it.
- **Headers.** Answers carry `Content-Language`, unless the endpoint set
  its own, and `Vary: Accept-Language` when `LANGUAGES` has more than one
  language. So shared caches keep a copy per language.
- **WebSockets** get the language too. Their messages are the
  application's to translate.
- Without the middleware, everything is in `LANGUAGE_CODE`.

`negotiate(header, languages, default)` is the function that the
middleware uses. You can call it yourself:

```python
from domainkit.i18n import negotiate

negotiate("ar-EG, ar;q=0.9, en;q=0.5", ["en", "ar"], "en")  # 'ar'
negotiate("fr", ["en", "ar"], "en")  # 'en'
negotiate("pt", ["en", "pt-br"], "en")  # 'pt-br'
negotiate(None, ["en"], "en")  # 'en'
```

`get_language()` returns the active language: `'en'` outside a request,
unless `override` set another.

## What is translated

- **The `detail` of every error answer**, as the body is built: the
  framework's own messages, the HTTP status phrases that Starlette uses
  for errors raised without a detail, and any message a catalog holds. A
  `DomainError`'s message is translated the same way, by its exact text.
  So the domain layer stays free of translation code: raise
  `InvoiceNotFound("No invoice has that number.")`, and add that sentence
  to a catalog.
- **Each validation `msg`**, by the template that pydantic writes it from.
  The catalogs translate `String should have at most {max_length}
  character{expected_plural}` once, and the error's context fills it in,
  with numbers written as the language writes them. A custom error type's
  message is looked up as it is.
- **Not** `code`, `type`, `loc`, `title`, or header names: clients rely
  on them.

A body with a 20-character `sku`, where 12 is the limit, gets this answer
in Arabic:

```json
{
  "detail": "الطلب غير صالح.",
  "code": "validation_error",
  "errors": [
    {"loc": ["body", "sku"], "msg": "يجب ألا يزيد عدد الأحرف على ١٢", "type": "string_too_long"}
  ]
}
```

`validation_message(error)` translates one pydantic error this way. It
takes the error as a dict, and returns `msg` as pydantic wrote it when no
catalog translates it:

```python
from domainkit.i18n import override, validation_message

error = {
    "type": "string_too_long",
    "msg": "String should have at most 12 characters",
    "ctx": {"max_length": 12},
}
with override("ar"):
    print(validation_message(error))
```

```text
يجب ألا يزيد عدد الأحرف على ١٢
```

A message is matched by its exact English text. A message built with
values inside (`f"No aggregate has id {id_}."`) has no fixed text, so it
stays in English. Write fixed messages, and put the values in fields of
their own.

## Your own messages

Mark text with the gettext functions. They have Django's names:

```python
from domainkit.i18n import gettext, gettext_lazy, ngettext, npgettext, pgettext

gettext("Your export is ready.")  # now, in the active language
ngettext("{n} invoice", "{n} invoices", n).format(n=n)  # plural forms
pgettext("menu", "Open")  # the same word in another sense (msgctxt)
npgettext("menu", "{n} file", "{n} files", n)  # both

TITLE = gettext_lazy("Invoices")  # at import time: translated when used
str(TITLE)
```

| Function | What it returns |
| --- | --- |
| `gettext(message)` | The translation in the active language, or `message`. |
| `ngettext(singular, plural, n)` | The plural form for `n`. English: `ngettext("{n} invoice", "{n} invoices", 3)` is `'{n} invoices'`. |
| `pgettext(context, message)` | The translation in a context (`msgctxt`), for a word with several senses. |
| `npgettext(context, singular, plural, n)` | Both: a context and plural forms. |
| `gettext_lazy(message)`, `ngettext_lazy(...)`, `pgettext_lazy(...)` | A `LazyString`, translated each time it is turned into text. |
| `gettext_noop(message)` | `message`, unchanged: it only marks the text for the catalogs. |

A `LazyString` is translated each time it is turned into text, in the
language active then. It compares, formats, and joins as its
translation does:

```python
from domainkit.i18n import gettext_lazy, override

TITLE = gettext_lazy("The request is invalid.")
print(str(TITLE))
with override("ar"):
    print(str(TITLE), TITLE == "الطلب غير صالح.")
```

```text
The request is invalid.
الطلب غير صالح. True
```

Use `gettext_noop` for text that is translated later. An error detail
is: the boundary translates it.

`override("ar")` makes a language active for a block, in a test or a
task:

```python
from domainkit.i18n import gettext, override

with override("ar"):
    assert gettext("The request is invalid.") == "الطلب غير صالح."
```

Use these functions in the `api` and `application` layers. The `domain`
layer may import only `domainkit.ddd`, so domain messages are plain
English, and the boundary translates them.

## Catalogs

Catalogs are gettext `.po` files, which translators' tools (Poedit,
Weblate, Crowdin) read and write. They are compiled to the `.mo` files
that `gettext` reads:

```text
src/domains/billing/locale/ar/LC_MESSAGES/messages.po
src/domains/billing/locale/ar/LC_MESSAGES/messages.mo
```

```po
msgid "No invoice has that number."
msgstr "لا توجد فاتورة بهذا الرقم."

msgid "{n} invoice"
msgid_plural "{n} invoices"
msgstr[0] "لا فواتير"
msgstr[1] "فاتورة واحدة"
msgstr[2] "فاتورتان"
msgstr[3] "{n} فواتير"
msgstr[4] "{n} فاتورة"
msgstr[5] "{n} فاتورة"
```

A message is looked up in the catalogs of its language in this order.
The first catalog that has it wins, so a project can reword the
framework's messages:

1. each directory of `LOCALE_PATHS`;
2. each installed domain's `locale` directory, in `INSTALLED_DOMAINS`
   order;
3. domainkit's own (English and Arabic).

A language with a region looks up its region first, then the language:
`pt-br` reads `pt_BR`, then `pt`. A catalog needs a header that says
`Content-Type: text/plain; charset=UTF-8`, and for plurals, its
`Plural-Forms` (Arabic has six forms; see domainkit's own `ar` catalog).

### Writing catalogs: `makemessages`

`makemessages` writes and updates a domain's catalogs from its code. It
reads each module (nothing is imported or run), and it collects the
literal strings passed to `gettext`, `_`, `gettext_lazy`, `ngettext`,
`ngettext_lazy`, `pgettext`, `pgettext_lazy`, and `npgettext`, with the
lines that use them:

```bash
python manage.py makemessages -l ar          # start or update ar, every domain
python manage.py makemessages -l ar billing  # one domain
python manage.py makemessages --all billing  # every locale billing has
python manage.py makemessages --check        # write nothing; fail if one is behind
```

- New messages are added untranslated. Translations and fuzzy flags are
  kept.
- A message that no code uses any more is kept as an obsolete `#~`
  entry. So a rename loses no translation, and using the message again
  brings it back.
- A message built at run time (an f-string, a variable) is not found: it
  could not be looked up in a catalog either.
- A new catalog's `Plural-Forms` is English's. Set the language's own in
  its header, and new plural messages then get its number of forms.
- A domain with nothing to translate gets no catalog. domainkit's own
  domains are left out.

### Compiling catalogs: `compilemessages`

Compile after every change, and check in CI that nobody forgot:

```bash
python manage.py compilemessages          # LOCALE_PATHS and every domain's locale
python manage.py compilemessages -l ar    # one language
python manage.py compilemessages --check  # write nothing; fail if one is stale
```

- `compilemessages` is written in Python, so you do not need GNU gettext.
  Its output depends only on the `.po` file: the same catalog always
  gives the same bytes.
- It leaves out fuzzy and untranslated entries, as `msgfmt` does.
- It refuses a catalog whose translation names a `{placeholder}` that its
  message does not have, or a plural entry with the wrong number of
  forms, and names the line.
- It also takes directories to compile: `compilemessages path/to/locale`.
- Catalogs are read once per process: restart after you compile.

You may also extract messages with the tools that translators use, for
example GNU `xgettext` or Babel:

```bash
xgettext --language=Python --from-code=UTF-8 --keyword=gettext_lazy \
  --keyword=pgettext:1c,2 --keyword=ngettext_lazy:1,2 --output=messages.pot \
  $(git ls-files 'src/domains/billing/*.py')
```

### Adding a language

1. List it in `LANGUAGES`: `LANGUAGES = [("en", "English"), ("ar",
   "Arabic"), ("fr", "French")]`. Codes are lower case.
2. Write its catalogs: `python manage.py makemessages -l fr`, then
   translate them.
3. Compile them: `python manage.py compilemessages`.
4. Register its number and date formats ([below](#numbers-and-dates)) if
   they are not English's.

## Time zones

Dates are stored and compared in UTC: `UTCDateTime` columns refuse naive
values, and events carry aware times. `TIME_ZONE` only says how to show
them, and what "today" is for the business:

```python
TIME_ZONE = "Africa/Cairo"
```

```python
from datetime import UTC, datetime

from domainkit.i18n import localdate, localtime, timezone

issued = datetime(2026, 10, 19, 13, 4, tzinfo=UTC)
localtime(issued)  # 2026-10-19 16:04:00+03:00: the same moment, in TIME_ZONE
localdate(issued)  # 2026-10-19
localdate()  # today in TIME_ZONE (the UTC date may differ)
timezone.now()  # the current time, aware, in UTC: what to store

with timezone.override("Asia/Riyadh"):  # one caller's zone, for a block
    localtime(issued)  # 2026-10-19 16:04:00+03:00
```

- `localtime(value=None, timezone=None)` and
  `localdate(value=None, timezone=None)` take an aware datetime (now, if
  none) and an optional zone in place of the current one.
- `localtime` refuses naive datetimes, because their zone is unknown:
  `ValueError: localtime() needs an aware datetime; a naive one's zone is
  unknown.`
- `timezone.now()` is `domainkit.clock.now()`, so `freeze_time` in a test
  stops it, and "today" with it ([testing.md](testing.md)).
- `timezone.override(zone)` takes a zone name or a `tzinfo`.
- Zones come from the system's time zone database. Where there is none
  (some slim container images), add the `tzdata` package. An unknown
  `TIME_ZONE` fails at startup.

## Numbers and dates

The format functions write numbers and dates as the active language
does:

```python
from datetime import UTC, datetime
from decimal import Decimal

from domainkit.i18n import date_format, datetime_format, number_format, time_format

issued = datetime(2026, 10, 19, 13, 4, tzinfo=UTC)
number_format(1234.5)  # "1,234.5"
number_format(Decimal("2.675"), 2)  # "2.68": half to even
date_format(issued)  # "Oct 19, 2026", in TIME_ZONE
date_format(issued, "long")  # "October 19, 2026"
date_format(issued, "full")  # "Monday, October 19, 2026"
time_format(issued)  # "4:04 PM"
datetime_format(issued, "medium", "short")  # "Oct 19, 2026, 4:04 PM"
```

The same calls inside `override("ar")` returned:

```text
١٬٢٣٤٫٥
٢٫٦٨
١٩‏/١٠‏/٢٠٢٦
١٩ أكتوبر ٢٠٢٦
٤:٠٤ م
١٩‏/١٠‏/٢٠٢٦، ٤:٠٤ م
```

- Formats follow the Unicode CLDR's `en` and `ar` (Arabic with
  Arabic-Indic digits, as CLDR's `ar` does).
- Date styles are `short`, `medium` (the default), `long`, and `full`.
  Time styles are `short` (the default) and `medium`.
- Aware datetimes are shown in the current time zone.
- A language without formats of its own uses its primary subtag's
  (`ar-eg` uses `ar`), then English's.

Register other formats, or change one, at startup (in
`DomainConfig.ready()`). `domainkit.i18n.formats` has `ARABIC`, a
`LocaleFormats`, and `register_formats`:

```python
from dataclasses import replace

from domainkit.i18n.formats import ARABIC, register_formats

register_formats("ar-ma", replace(ARABIC, digits="0123456789", decimal=","))
```

With `override("ar-ma")`, `number_format(1234.5)` then returns
`'1٬234,5'`, and `date_format(issued, "long")` returns
`'19 أكتوبر 2026'`.

Prefer to send numbers and ISO 8601 dates as data, and to format them in
the client. Format on the server only for text that people read as it
is: an email, a PDF, a notification.

## Caches and languages

An answer that depends on the language must be cached per language.
`LocaleMiddleware` adds `Vary: Accept-Language` for shared caches, and
`cache_page` keys every entry by the active language
([cache.md](cache.md#caching-whole-responses)).

## Options

The settings; the [settings reference](reference/settings.md#languages-and-time-zones)
has the full rows:

| Setting | Default | What it does |
| --- | --- | --- |
| `LANGUAGE_CODE` | `"en"` | The language when `Accept-Language` asks for none of `LANGUAGES`, and outside requests. It must be one of them. |
| `LANGUAGES` | `(("en", "English"), ("ar", "Arabic"))` | `(code, name)` of each language answers may be in. |
| `LOCALE_PATHS` | `()` | Directories of catalogs, looked up before each domain's `locale` directory. |
| `TIME_ZONE` | `"UTC"` | The zone dates are shown in. Dates are stored in UTC whatever it says. |

The commands; the [commands reference](reference/commands.md) has the
full list:

| Command | Options |
| --- | --- |
| `makemessages [DOMAIN ...]` | `-l`/`--locale` (repeatable), `--all` (every locale a domain has), `--check` |
| `compilemessages [DIRECTORY ...]` | `-l`/`--locale` (repeatable), `--check` |

## Errors and refusals

| What you see | Why | What to do |
| --- | --- | --- |
| A message stays in English | No catalog has its exact text, the catalog is not compiled, or the process started before you compiled. | Add it with `makemessages`, compile, restart. |
| `compilemessages` fails, naming a line | A translation names a placeholder that its message lacks, or a plural entry has the wrong number of forms. | Fix the entry. |
| `makemessages --check` or `compilemessages --check` fails in CI | A catalog is behind the code, or a `.mo` file is stale. | Run the command without `--check`, and commit. |
| `ValueError` from `localtime` | A naive datetime. | Store and pass aware UTC datetimes. |
| Startup fails on `TIME_ZONE` | The zone is unknown, or the system has no time zone database. | Fix the name, or install `tzdata`. |
| Startup fails on `LANGUAGE_CODE` | It is not one of `LANGUAGES`. | Add it to `LANGUAGES`. |

## Common mistakes

- **Building a message with an f-string.** It has no fixed text, so no
  catalog can translate it. Write a fixed message, and put the values in
  fields of their own.
- **Calling `gettext` at import time.** The text is translated once, in
  the language active then. Use `gettext_lazy` for module-level text.
- **Forgetting to compile.** `.po` files are not read; `.mo` files are.
  Run `compilemessages`, and `compilemessages --check` in CI.
- **Formatting numbers on the server for an API.** Clients cannot read
  `١٬٢٣٤٫٥` back as a number. Send numbers as data, and format them in
  the client.
- **Storing local times.** Store UTC; show in `TIME_ZONE` with
  `localtime`.

# Languages, time zones, and formats

An API answers machines first: clients should act on `code` and `type`,
which never change. People read `detail` and the validation messages,
though, and they read them best in their own language. domainkit
translates the framework's messages into Arabic, lets projects add their
own languages and messages, shows stored UTC times in the business's time
zone, and writes numbers and dates as each language writes them. The
decision is in [ADR 0039](adr/0039-translate-messages-at-the-boundary.md).

## Answering in the caller's language

Add `LocaleMiddleware` before `RequestContextMiddleware`, so the errors that
and every later middleware answer with are translated too:

```python
MIDDLEWARE = [
    "domainkit.http.middleware.ProxyHeadersMiddleware",
    "domainkit.http.locale.LocaleMiddleware",
    "domainkit.http.middleware.SecurityHeadersMiddleware",
    "domainkit.http.middleware.RequestContextMiddleware",
    ...,
]
LANGUAGE_CODE = "en"  # when the caller asks for nothing we have
LANGUAGES = [("en", "English"), ("ar", "Arabic")]
```

```http
POST /auth/login
Accept-Language: ar-EG, ar;q=0.9, en;q=0.5

HTTP/1.1 401 Unauthorized
Content-Language: ar
Vary: Accept-Language

{"detail": "تعذّر تسجيل الدخول ببيانات الاعتماد المقدَّمة.", "code": "invalid_credentials", "request_id": "..."}
```

- The middleware reads `Accept-Language` and picks the language of
  `LANGUAGES` it prefers most: by `q`, then in order. `ar-eg` matches
  `ar`, and `pt` matches `pt-br`. A missing header, `*`, or nothing that
  matches gives `LANGUAGE_CODE`. Malformed ranges are skipped, and only the
  first 32 ranges (1,024 characters) are read.
- The language is the request's for its whole run, in a context variable:
  `gettext` in endpoints and tasks started from the request use it.
- Responses carry `Content-Language`, unless the endpoint set its own, and
  `Vary: Accept-Language` when `LANGUAGES` has more than one language, so
  shared caches keep a copy per language.
- WebSocket connections get the language too; their messages are the
  application's to translate.
- Without the middleware, everything is in `LANGUAGE_CODE`.

## What is translated

- The `detail` of every error response, as the body is built: the
  framework's own messages, the HTTP status phrases Starlette uses for
  errors raised without a detail, and any message a catalog holds. A
  `DomainError`'s message is translated the same way, by its exact text,
  so the domain layer stays free of i18n: raise
  `InvoiceNotFound("No invoice has that number.")`, and add that sentence
  to a catalog.
- Each validation `msg`, by the template pydantic writes it from: the
  catalogs translate `String should have at most {max_length}
  character{expected_plural}` once, and the error's context fills it in,
  numbers written as the language writes them. A custom error type's
  message is looked up as it is.
- Not `code`, `type`, `loc`, or header names: clients rely on them.

A message is matched by its exact English text. A message built with
values inside (`f"No aggregate has id {id_}."`) has no fixed text, so it
stays in English: write fixed messages, and put the values in fields of
their own.

## Your own messages

Mark text with the gettext functions, Django's names:

```python
from domainkit.i18n import gettext, gettext_lazy, ngettext, pgettext

gettext("Your export is ready.")  # now, in the active language
ngettext("{n} invoice", "{n} invoices", n).format(n=n)  # plural forms
pgettext("menu", "Open")  # the same word in another sense (msgctxt)

TITLE = gettext_lazy("Invoices")  # at import time: translated when used
str(TITLE)
```

`gettext_lazy` returns a `LazyString`: it is translated each time it is
turned into text, in the language active then, and compares, formats, and
concatenates as its translation. `gettext_noop` marks a message for the
catalogs without translating it, for text translated later (an error
detail is, at the boundary). `override("ar")` makes a language active for a
block, in a test or a task:

```python
from domainkit.i18n import override

with override("ar"):
    assert gettext("The request is invalid.") == "الطلب غير صالح."
```

Use these in the `api` and `application` layers. The `domain` layer may
import only `domainkit.ddd`, so domain messages are plain English, and the
boundary translates them.

## Catalogs

Catalogs are gettext `.po` files, which translators' tools (Poedit,
Weblate, Crowdin) read and write, compiled to the `.mo` files `gettext`
reads:

```text
src/domains/billing/locale/ar/LC_MESSAGES/messages.po
src/domains/billing/locale/ar/LC_MESSAGES/messages.mo
```

```po
msgid "No invoice has that number."
msgstr "لا توجد فاتورة بهذا الرقم."

msgid "{n} invoice"
msgid_plural "{n} invoices"
msgstr[0] "لا فواتير"
msgstr[1] "فاتورة واحدة"
msgstr[2] "فاتورتان"
msgstr[3] "{n} فواتير"
msgstr[4] "{n} فاتورة"
msgstr[5] "{n} فاتورة"
```

A message is looked up in the catalogs of its language in this order, and
the first that has it wins, so a project can reword the framework's
messages:

1. each directory of `LOCALE_PATHS`;
2. each installed domain's `locale` directory, in `INSTALLED_DOMAINS` order;
3. domainkit's own (English and Arabic).

A language with a region looks up its region first, then the language:
`pt-br` reads `pt_BR`, then `pt`. A catalog needs a header that says
`Content-Type: text/plain; charset=UTF-8`, and for plurals, its
`Plural-Forms` (Arabic has six forms; see domainkit's own `ar` catalog).

Compile after every change, and check in CI that nobody forgot:

```bash
python manage.py compilemessages          # LOCALE_PATHS and every domain's locale
python manage.py compilemessages -l ar    # one language
python manage.py compilemessages --check  # write nothing; fail if one is stale
```

`compilemessages` is written in Python, so GNU gettext is not needed, and
its output depends only on the `.po` file: the same catalog always gives
the same bytes. It leaves out fuzzy and untranslated entries, as `msgfmt`
does, and refuses a catalog whose translation names a `{placeholder}` its
message does not have, or a plural entry with the wrong number of forms,
naming the line. Catalogs are read once per process: restart after
compiling.

To list the messages to translate, extract them with the tools translators
use, for example GNU `xgettext` or Babel:

```bash
xgettext --language=Python --from-code=UTF-8 --keyword=gettext_lazy \
  --keyword=pgettext:1c,2 --keyword=ngettext_lazy:1,2 --output=messages.pot \
  $(git ls-files 'src/domains/billing/*.py')
```

To add a language, list it in `LANGUAGES`, add its catalogs, and register
its number and date formats (below) if they are not English's.

## Time zones

Dates are stored and compared in UTC: `UTCDateTime` columns refuse naive
values, and events carry aware times. `TIME_ZONE` only says how to show
them, and what "today" is for the business:

```python
TIME_ZONE = "Africa/Cairo"
```

```python
from domainkit.i18n import localdate, localtime, timezone

localtime(invoice.issued_at)  # the same moment, in TIME_ZONE
localdate()  # today in TIME_ZONE (the UTC date may differ)
timezone.now()  # the current time, aware, in UTC: what to store

with timezone.override("Asia/Riyadh"):  # one caller's zone, for a block
    localtime(invoice.issued_at)
```

`localtime` refuses naive datetimes: their zone is unknown. Zones come
from the system's time zone database; where there is none (some slim
container images), add the `tzdata` package. An unknown `TIME_ZONE` fails
at startup.

## Numbers and dates

```python
from domainkit.i18n import date_format, datetime_format, number_format, time_format

number_format(1234.5)  # "1,234.5"; in Arabic, Arabic-Indic digits and marks
number_format(Decimal("2.675"), 2)  # "2.68": half to even
date_format(invoice.issued_at)  # "Oct 19, 2026" in TIME_ZONE; "١٩‏/١٠‏/٢٠٢٦"
date_format(day, "long")  # "October 19, 2026"; "١٩ أكتوبر ٢٠٢٦"
time_format(invoice.issued_at)  # "3:04 PM"; "٣:٠٤ م"
datetime_format(invoice.issued_at, "medium", "short")
```

Formats follow the Unicode CLDR's `en` and `ar` (Arabic with Arabic-Indic
digits, as CLDR's `ar` does). Date styles are `short`, `medium`, `long`,
and `full`; time styles `short` and `medium`. Aware datetimes are shown in
the current time zone. A language without formats of its own uses its
primary subtag's (`ar-eg` uses `ar`), then English's. Register others, or
change one, at startup (in `DomainConfig.ready()`):

```python
from dataclasses import replace

from domainkit.i18n.formats import ARABIC, register_formats

register_formats("ar-ma", replace(ARABIC, digits="0123456789", decimal=","))
```

Prefer sending numbers and ISO 8601 dates as data, and formatting them in
the client. Format on the server only for text people read as it is: an
email, a PDF, a notification.

## Caches and languages

A response that depends on the language must be cached per language.
`LocaleMiddleware` adds `Vary: Accept-Language` for shared caches, and
`cache_page` keys every entry by the active language
([cache.md](cache.md#caching-whole-responses)).
